# MARK1_DIFF CAN 协议及证据边界

证据来源：旧工程 `f90f687` 的 CAN 编解码定义、用户提供的前次实测，以及 [2026-10-27 新驱动实测](validation.md)。不把旧工程中的字段假设自动当作设备事实。

## 总线与身份

500000 bit/s，经典 CAN，29 位扩展 ID：

```text
id = (class << 24) | (type << 16) | (node << 8) | function
class=0x01, type=0xE1, node=0x01  =>  0x01E101xx
```

多字节整数以小端解析。应用内保存纯 ID；Linux 的 `CAN_EFF_FLAG` 仅在 SocketCAN 边界添加/去除。类别 `0x05` 是下游驱动器，禁止与整车 `0x01` 共享解码入口。

## 发送

从 GUI 操作查找具体帧及发送时序，见 [GUI 功能与 CAN 帧对应关系](gui-can.md)。下表说明协议字段，该文说明当前按钮如何使用这些字段。

| 功能码 | 字节 | 内容及证据 |
|---|---:|---|
| 01 | 3 | `01 E1 01`；仅保留显式单次复位接口，恢复行为未验证可靠 |
| 02 | 0 | 查询版本，A2 应答 |
| 03 | 5 | `01 E1 01 en 01`；A3 零载荷应答，另由 B0 确认使能 |
| 04 | 1 | `CC` 清故障；A4；未人为制造硬件故障，因此不宣称清障效果已验证 |
| 05 | 1 | `CC` 清运动计数；A5；本次另观察 B3 与四路 B7 确认归零 |
| 11 | 4 | `mode beep brake special`；mode=0/1/2/3；只验证 mode/beep 状态 |
| 12 | 6 | `int16 vx×1000, int16 vy×1000, int16 wz×1000`；ROS 差速入口固定发送 vy=0 |
| 15–18 | 1 | `00/01`，分别控制 B5/B6/B7/B8；没有已知 ACK |

速度编码四舍五入至 0.001 单位，非有限值和超出 int16 表示范围的值在纯协议库拒绝。ROS 命令层先按参数限幅。只有收到新速度时才开始周期重发；超时一次零速后静默。不要用保持旧速度无限重发来替代上层命令时效。

## 接收

| 功能码 | 实机长度 | 解析 / 验证状态 |
|---|---:|---|
| A2 | 8 | 两段各 4 字节 ASCII，零终止或恰好四字符；实测 `3.0`、`4.0` |
| A3/A4/A5 | 0 | 对应 03/04/05 的接收确认；不读取载荷 |
| B0 | 1 | D0 使能 0/1，约 500 ms |
| B1 | 6 | D0 工作状态、D1 模式、D2–D3 int16/10 V、D4 蜂鸣器、D5 原样保留 |
| B2 | 6 | 三个 int16/1000，vx/vy/wz，约 20 ms；低速反馈有明显抖动 |
| B3 | 8 | 左右 int32 毫米，约 20 ms；方向与清零已实测 |
| B4 | 未观察 | 按旧定义解析两路 int32 副轮毫米；缺失不算当前车型故障 |
| B5 | 7 | D0 四个 2-bit 开关，D1–D6 int8 摇杆；开关生效，实机摇杆变化仍未验证 |
| B6 | 未观察 | 旧定义 D0 碰撞位、D1–D6 六路传感原始值；单位不猜测 |
| B7 | 7 | D0 channel，D1–D2 int16 RPM，D3–D6 int32 脉冲；总周期约 20 ms |
| B8 | 8 | D0 channel，D1–D2 int16/10 V，D3–D4 int16/10 A，D5/D6 int8 温度，D7 原始故障位；总周期约 100 ms |
| BA | 未观察 | 沿用前 5 字节偏移，保持原始错误码；至少 5 字节，不宣称硬件故障语义已验证 |

B7/B8 channel 必须是 0–3；ROS 消息同时给出 `driver_id=channel+1`。不通过未检查的 channel 索引任何数组。

B1 解码支持 6 或 8 字节，仅使用已知的前 6 字节。D5 未识别，不能直接称为“遥控丢失”；D6/D7 在实机报文中不存在，不读取也不输出刹车/特殊功能布尔状态。所有帧先校验长度，缓冲区全零初始化。

B6、B4、BA 没出现不构造虚假的“零值正常”反馈。B8 故障位虽然有旧定义，新接口保留 raw 值以避免把未经验证的解释固定到 API 中。

## 复位与看门狗

用户前次记录：发送 `01E10101#01E101` 后整车心跳和下游报文停止，查询无应答并出现发送错误；重建宿主 can0、清待发队列并恢复 500 kbit/s 后恢复通信。无法由这些证据区分设备启动时间、适配器状态与队列问题。新驱动没有在本次再次执行复位，也没有把它标为通过。

用户前次实测设备不再收到运动命令后约 498–501 ms 将四路目标归零。新驱动使用独立的约 300 ms ROS 输入超时，实机本次测得零速报文延迟约 307 ms。两个数字对应不同层，不把本次主机超时测试当作重新验证了固件 500 ms 看门狗。
